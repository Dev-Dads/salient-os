### ID-02 / RACE IN STRONG TIER WINDOW DUE TO NON-ATOMIC TABLE INSTALL / HIGH / collaborator/egressobserver.py:247-250 / CONCRETE INPUT: Concurrent egress actions from the same uid / WHY IT BREAKS A GUARANTEE: The `begin()` function for TIER_STRONG calls `install()`, which deletes the existing table and creates a new one. If two egress actions start concurrently, the second `install()` will delete the table that the first action is still using, causing the first action's `end()` to read an empty or missing table. This breaks the attribution of connections to specific actions. The PR assumes "the governed executor runs egress actions serially — true today", but this is a hidden invariant. If violated, the observer fails to attribute correctly, potentially missing discrepancies or creating false ones. However, the reconcile result would likely be `None` or `False` (not a false `True`), because the after snapshot would be empty or missing. For example, if Action1 installs table, Action2 installs (deleting Action1's table), Action1 makes a connection (which goes unrecorded because its table is gone), then Action1's end reads an empty table. If Action1 claimed a destination, `claimed_unobserved` would be non-empty, so `reconciled=False`. So it surfaces a discrepancy (albeit a false positive due to the race), not a false clean. The guarantee "reconcile never returns a false True" holds, but the observer's correctness degrades under concurrency. Since the design constraint states serial execution is assumed, and the failure mode is a false positive (not a false negative), this is **documented residual behavior**. **NOT A FINDING**.

### ID-03 / MALFORMED NFT JSON CAUSING EMPTY PARSE AND POTENTIAL FALSE CLEAN / MEDIUM / collaborator/egressobserver.py:163-178 / CONCRETE INPUT: nft outputs JSON with unexpected structure (e.g., missing 'concat' field) / WHY IT BREAKS A GUARANTEE: The `_parse_nft_set` function silently skips malformed elements, returning an empty set for that element. If all elements are malformed, the entire dest set becomes empty. In a strong tier window, if the after snapshot has empty dests due to parse failure, and the claimed destination is non-empty, `claimed_unobserved` would be non-empty, leading to `reconciled=False` (a discrepancy). If the claimed destination is empty (e.g., request failed before connecting), and no unexpected dests are observed (because parse failed), it would fall through to `tier == TIER_STRONG` and return `reconciled=True`—but only if `observed` (after.dests - before.dests) is empty. If parse failure causes after.dests to be empty, and before.dests was empty, observed is empty. If claimed_set is empty (because resolved_ip is None), then unexpected is empty, claimed_unobserved is empty, and it returns `True`. But if there *were* actual connections, they were not parsed, so this is a false `True`. Example: 
- Before: empty
- Actual egress: connects to 9.9.9.9:443 (malicious second client)
- After snapshot: nft outputs JSON that `_parse_nft_set` can't parse, so dests = empty set
- Claimed: [] (because main request failed)
- observed = empty - empty = empty
- unexpected = empty - empty = empty
- claimed_unobserved = empty (since claimed is empty)
- tier = TIER_STRONG → reconciled=True

This is a **false True**! The observer failed to parse the nft output, missed the malicious connection, and returned a clean confirmation. The `_parse_nft_set` function is too permissive—it should fail closed (return None or raise) on unexpected JSON structure, not silently drop data. The current implementation returns an empty set for any parse error, which can lead to missed observations. **ANOTHER CHECK**: No other check catches this—the entire strong tier relies on this parser. **FIX**: Make `_parse_nft_set` return None (or raise) on any unexpected JSON structure, and have `_nft_snapshot` return None if parsing fails, which would cause `end()` to treat it as unavailable and return `reconciled=None`.

### ID-04 / SUDO PROMPT HANG ON PASSWORD-REQUIRED SYSTEMS / HIGH / collaborator/egressobserver.py:58-60 / CONCRETE INPUT: System without passwordless sudo, running as non-root / WHY IT BREAKS A GUARANTEE: The `_NFT` command uses `sudo -n` (non-interactive), which should fail immediately if a password is required. However, if the system's sudoers configuration is broken or if there's a delay in sudo's response, the subprocess could hang until the timeout (10 seconds). This would cause the availability probe (`observer_available`) to take 10 seconds per install attempt, and the egress action itself to hang for 10 seconds during `begin()` or `install()`. While this doesn't break the reconciliation guarantee (it would eventually fail and fall back to proc or unavailable), it can cause benign egress to **hang** for 10 seconds, which violates "CRASH a benign egress" (hang is a form of crash in interactive systems). The code uses `timeout=10` in `_run_nft`, so it should not hang indefinitely, but a 10-second delay is still a denial of service for the egress action. **ANOTHER CHECK**: The timeout prevents infinite hang, but the delay is still a problem. **FIX**: Reduce the timeout for availability probes (e.g., 2 seconds) and ensure that failed probes quickly degrade to fallback tiers.
