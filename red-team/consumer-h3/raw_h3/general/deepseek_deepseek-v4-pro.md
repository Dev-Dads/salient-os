Now, consider a scenario: the session starts, turn 1 runs, directive emitted and cached. Then the process crashes. On restart, the bus file exists. It constructs a bus (which replays the file), reads the last directive, caches it, returns the budget. That budget is applied. So they should match. So no issue.

But what if the config changed between the crash and restart? Then the pristine is the new config's value, and _operator_budget() reads the new config. So they match. The directive from the previous process might have a budget based on the old config's floor. That budget could be outside the new window. The consumer will apply it verbatim. That's the resume caveat: "the first turn of a resumed session reapplies the LAST RECORDED budget for that session — with headroom on, simply ending on a busy turn is enough (no config change needed): the recorded value can sit anywhere in the prior window, above OR below the current operator setting, until the next turn is finalized." So that's documented and accepted. So not a defect.

Now, the main defect remains the produce-path floor mismatch within the same process.

Let's craft a concrete trigger for that:

1. Set environment variable HERMES_MAX_ITERATIONS=100 (which the host uses to set agent.max_iterations).
2. Config file has agent.max_iterations=25 (or no agent.max_iterations, so _operator_budget returns 25).
3. Headroom=15.
4. Start the agent. The pristine captured will be 100.
5. Turn 1: consumer returns default 100. Turn runs, does 8 events.
6. Turn 2 starts: pre_llm_call for turn 2 triggers rollover close of turn 1's window with budget=None -> _operator_budget()=25. Directive recorded: floor=25, headroom=15, budget=40.
7. Turn 2's consumer calls bounded_iterations with default=100. It finalizes turn 1's window (already closed), reads directive, gets 40, returns 40.
8. Turn 2 gets budget 40, which is below the operator floor of 100. Violation.

This is a concrete, plausible scenario if the host supports HERMES_MAX_ITERATIONS. The host's cli.py might read that env var. The observer's _operator_budget deliberately ignores it. So it's a real bug.

Severity: HIGH, because it breaks the bounded escalation guarantee and could lead to the agent getting fewer iterations than the operator intended, potentially causing it to fail to complete tasks.

Fix: The produce-path close should use the same floor as the consumer's default, i.e., the pristine operator budget. Since the observer doesn't have access to the agent, we need to pass the pristine budget to the observer for use in rollover closes. One way: store the pristine budget in a module-level variable that the call site sets, or pass it as an argument to the close functions. Alternatively, change _operator_budget to read the same source as the pristine, including the env var. The docstring says it deliberately doesn't read the env var, but that decision is causing the mismatch. So either read the env var or have the call site pass the budget.

Given the context, the call site already captures the pristine. It could pass it to the observer via a new function, or the observer could accept a budget override. But that's a design change.
